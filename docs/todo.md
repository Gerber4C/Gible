## Design Notes To Revisit

1. Public partnership meaning and internal training origin are separate output layers.
2. A selected bid should report which rule and gadget produced it.
3. Judgmental choices should report compared candidate rules, not only the final selected rule.
4. Gadgets and rules need author metadata.
5. Human-authored IDs should stay short, with fully qualified origin names generated by the engine.
6. Selection reasoning must be structured and machine-readable. Natural-language display text can be generated from structured criterion results, but it should not be the source of truth.
7. Custom gadget/rule selection algorithms need a practical plugin interface.
8. LLM-generated gadgets must remain drafts until validated and approved. The structured gadget file is the source of truth, not the natural-language prompt.
9. Keep tournament/inter-user features separated from the system execution engine so the engine remains useful as a standalone authoring, training, and analysis tool.
10. A basic system, such as 2/1, is a user-facing concept. Technically it is just a gadget. Do not add unnecessary backend fields or object types that distinguish "basic system" from other gadgets unless a concrete implementation requirement appears.
11. Rule IDs should name what the rule does, not generic concepts like `meaning`. A rule is a formal call rule with optional selection, meaning, semantic effects, and default-policy behavior.
12. Before using any default behavior for an undefined auction, the engine should search all active gadgets globally for matching rules.
13. The ontology is a system-level contract. Gadget YAML, engine code, generated system notes, alert analysis, and LLM-assisted gadget drafting should share the same formal vocabulary.
14. The engine executes validated IR. BSL, natural-language notes, LLM drafts, and GUI forms are authoring layers that must compile or validate before use.
