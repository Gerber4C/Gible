# Axiom 公理层

公理先于 Policy 筛选候选，并在 Policy 返回后复查。普通候选、体系默认叫品、引擎兜底均受约束。无合规候选时返回 `call: null`，不伪造 Pass。

## 叫品标志

BSL 中通过 `call.meaning.axiom_tags` 声明，取值为：

`forcing`, `game_forcing`, `invite`, `invite_plus`, `invite_minus`, `accept`, `reject`, `signoff`。

这些标志**可选**，表示某一口叫品确实承担了对应含义；公理不要求每一口
都贴邀请、逼局、止叫等标签。例如普通第一口开叫无需贴这些标签，雅可比
转移也不必为了通过实力检查而假称邀请。未标记的非 Pass 中间叫品可按体系
定义继续拍卖；一旦体系明确赋予标签，公理就验证其含义与当前义务是否
相容。未标记本身不使叫品成为逼叫，也不替体系补写后续。

同时兼容既有 `call_act_types` 中的 `forcing`、`game_forcing`、`invitation`、`invitational`、`signoff`；`final_placement` 视为止叫。两种表达共同形成语义，不用动作名称猜测接受或拒绝。

```python
call.meaning.axiom_tags = ['accept', 'signoff']
call.meaning.nature = ['natural']
call.meaning.hcp_range = [12, 14]
```

Pass 带逼叫、逼局、邀请相关标志时，必须满足右手敌方刚作出非 Pass 叫品这一前提。敌方 Pass 后的这种定义会报 `PASS_SEMANTICS`。精确进程可以在加载时检查；通配进程在候选生效时检查。

## 已实现的六项公理

1. **逼叫**：同伴上一轮的逼叫义务尚未履行、右敌 Pass 时，不能 Pass。右敌非 Pass 时重新解释当前义务，允许有含义的 Pass。历史回放会保留这种 Pass 的含义、行动方、位置及效果。
2. **逼局**：本方逼局持续至本方达到自然成局定约，或满足明确的 4m 例外。敌方成局、人工 3NT 均不解除本方义务。Pass 若使敌方再 Pass 后同伴没有发言机会，则被禁止；非 Pass 的局下终结候选也被排除。
3. **进局**：自己 HCP 加同伴公开保证的下限达到门槛时，终结性 Pass 或明确止于局下的叫品被排除；自然成局、逼叫/询问/满贯探索，以及未作强度承诺的非 Pass 中间叫品可继续。中间叫品不能仅凭这一许可声称自己逼叫。
4. **邀请**：保证实力距门槛差 1–2 点，且同伴上限能够补足时，明确标为邀请的叫品可发起邀请；未作强度承诺的中间叫品不因此被拒绝。回答同伴的邀请/邀请+仍是明确义务：按自己已表示的范围判断，宽度 1 取上限；宽度 2 取好的中间值或上限；宽度至少 3 取下限+2 以上。答叫须有接受或拒绝的相应含义；接受不得止于局下，公开接受建立后续进局承诺。
5. **止叫**：自己 HCP 加同伴上限仍不够局时，明确标为邀请的叫品会被拒绝；邀请−、止叫或未作强度承诺的非 Pass 中间叫品可继续。若体系叫品声明可检验的替代点力证据（当前为 K–R 加所采用的同伴最低值），且确实达到该花色的成局门槛，公理也允许其逼局路线；这用于 6–5 等畸形牌，不把原始 HCP 止叫判断误当成绝对结论。已有应答义务先被处理，止叫不能覆盖逼叫/逼局。未触发邀请不等于必然不够局。
6. **点力质量**：采用下述 K–R 算法，质量影响宽度 2 时的中间值判断，不直接加到 HCP 上。

同伴待应答邀请优先于新邀请发起。询问/接力应答不被通用的进局、邀请或止叫分类替换。邀请到满贯暂不使用进局邀请公式。

## 拟增第七项：定将公理

定将适合与前六项并列，但其通用部分是**公开状态及转移顺序**，
而不是把某个叫品的含义强加给所有体系。状态分为：

- **未定将**：没有待确认或已确认的将牌。
- **准定将**：公开记录待确认花色及建立它的叫品；等待同伴的下一口。
- **定将**：公开记录已确认的唯一将牌。

定将记录的是后续问叫、扣叫等约定所参照的花色，**不是最终定约必须选择
该花色**。本方可以在低花定将后选择 3NT，或继续自然寻找高花；除非体系
明确给出改变定将状态的叫品，这些探索本身不清除已定的低花。体系中已无
满贯可能的进程，Daqiush 暂不要求推导定将状态；是否仍有满贯可能应按
公开叫牌含义判断，不读取两手实际牌张来回填状态。

**收束与定将分开处理**：只有体系没有可用的后续叫品、需要一步选择最终
定约时，才把已定将花色作为收束决策的依据。最终定约可以是该花色，
也可以是 NT；定将状态本身不授权提前结束探索，不自动生成该花色的
最低合法叫品。收束候选仍须符合其他公理及该进程的体系约定。
Daqiush 的收束花色／NT 及阶数交由发牌模拟比较；模拟尚不可用时，
缺少后续规则就明确阻塞，不以“最低合法定将花色”代替最终定约。

在准定将状态，同伴下一口若被体系明示为“维持准定将”，状态继续；
若明示为“推翻”，执行该叫品声明的新状态（可由体系指定为未定将、
另一花色的准定将或定将）；否则**默认滑入定将**。
判读这同一口的含义时，已经按定将状态处理——例如该体系赋予定将
状态的 4NT／四阶新花权限立即适用。必须先识别叫品自身是否明示
“维持／推翻”，再作默认定将与叫品解释；一个明示推翻的 4NT 不能
先被误读成问 A。无敌方干扰时，若同伴下一口为 Pass，拍卖结束，
不再产生需要解释的后续叫品。若敌方插叫后同伴 Pass，且体系没有
将该 Pass 明示为维持或推翻，仍按默认规则由准定将转为定将；
此时拍卖未必结束，后续叫品按定将权限解释。

进入定将后获得哪些叫牌权限，**由体系自行定义**。Daqiush 暂定
4NT 为问该将牌的 A，四阶新花色原则上为扣叫；体系明示的自然叫品
例外优先，不能只凭“已定将＋新花色”覆盖它。其他体系不自动继承
这两条。
体系须明确标记建立准定将／定将、维持和推翻的叫品，并声明定将后
的含义及例外；Policy 不能临时改写这些语义。公理负责转移、判读
先后顺序和语义一致性，不凭叫品外观或真实同伴手牌推断将牌，也不
替体系创造候选叫品。

现有引擎已有公开 `agreed_suit` 状态供前六项公理读取；三态记录与
三态与默认转移已由 `trump_state` 实现，Daqiush 只声明了部分已确认的进程；
完整的体系语义一致性检查仍需继续补齐。

Daqiush 雅各比单跳斯普林特的六条路径已按明确约定直接写入
`agreed_suit`，并让后续 4NT 读取同一门高花。这是“直接定将”的
局部实例；准定将的体系叫品仍待列出。Daqiush 哪些
具体叫品建立准定将，等待体系作者后续列出。

## 第八项：目的公理

叫出一口牌时，发起人应记录**私人目的**和可预见的同伴答叫分支；
同伴正常答叫后按已记录的分支执行，不能在那一刻重新用 Policy
选择不同目标。目的属于发起叫牌的座位，不成为同伴公开承诺的一部分；
只有选中发起叫品时才写入该座位的 `private_memory.purposes`，
并记录叫品位置、目标将牌及必要的私人牌情。历史公开回放不凭实际同伴手牌
反推出发起人的目的。敌方在目的发起后作出非 Pass 叫品时，原目的标为
`disrupted`，交回体系处理竞争叫牌；没有竞争规则时明确阻塞。

首批可执行分支：

- Daqiush 南非德克萨斯若在发起时已选定“只打 4M”：开叫人直接叫
  4M，应叫人 Pass；开叫人叫 4M−1，应叫人叫 4M 止叫。这个目的的
  K–R 选路边界已采用体系作者确认的可调初值和正反牌例，不能把
  “均型 6NT 的合计 33 原始 HCP”套用于高花满贯。已分类的 17+ HCP
  6-3-2-2 手牌改走“关键张足够就冲满贯”的路线，发起时不存游戏止叫
  计划，并在任一 Texas 答叫后直接问关键张。其他尚未分类的 Texas
  后续保持阻塞。
- 仅当 4NT **是以定将花色问关键张**、且实际被发起人选中时，
  且叫品意义明确指定将牌时，自动记录问叫目的。普通 1430 答叫按公开意义与发起人自己的五关键张
  数合并：缺至少两张则尝试五阶将牌止叫；不缺关键张则冲六阶；缺一张
  时还需将牌 Q。若 Q 未明而五阶将牌以下仍能询问，则须使用体系定义的
  问 Q 续叫（当前尚未定义，明确阻塞）；若空间不足，按作者规则假定
  不缺 Q 冲六阶。答叫计数无法消歧、止叫不合法或缺少公开答叫意义时
  均阻塞。示量邀请、低花选局等其他 4NT 不建立这个目的。

目的公理产生的确定续叫仍须通过叫品合法性及其他公理检查；
执行后将目的标为 `completed`。目前不对未实现的满贯模拟伪造
“只打 4M／只要关键张合适就冲 6M”的选路结果。
体系若在一口自然定约叫品上同时标记 `final_placement` 与
`purpose_completed: true`，则下一次轮到同伴、右敌 Pass 且该定约仍为
本方最后定约时，目的公理自动产生 Pass。它仍要通过逼叫、逼局和进局
检查；敌方改叫后不自动 Pass。只有已明示完成目的的叫品才享有此收尾，
不能因叫到 3NT 或 5m 就推断所有进程都应停叫。体系无需在每条此类
进程后重复编写一个 Pass 叫品。
静态的私人计划会在加载体系时检查类型、将牌和叫品格式；不完整定义返回
`INVALID_PURPOSE`，不等到牌桌上才发生程序异常。旧体系若未在问叫意义中
明确指定将牌，仍沿用其既有续叫，不擅自推断一个新的私人目的。

## 实力与质量的口径

当前实力范围统一使用 **HCP**。公开含义支持 `hcp_range`、`hcp_min`、`hcp_max`；公开状态效果支持 `opener.hcp`、`responder.hcp`、`actor.hcp`、`partner.hcp` 或座位 `.hcp` 的 `min_value`/`max_value`/`value`。

按行动方及一方内的开叫/应叫角色收集并取交集，保留来源。私有状态、另一方的范围不参与判断。公理不读取模拟器提供的真实同伴手牌。范围矛盾会报错；邀请应答缺少上下限或只有精确值时，明确报覆盖不足，不捏造范围。

K–R 使用 Richard Pavlicek 发布的 [26 步算法](https://rpbridge.net/8j19.htm)，来自用户指定的 [Point Count Methods](https://rpbridge.net/ac01.htm)。逐花色保存计算依据，内部按 1/20 点精度计算，原始结果为 `kr_points`。

**项目采用的好坏分类**：`K–R − HCP >= 0.5` 为好。这条分界是项目选择，不是原文定义；可配置。原始 HCP、K–R、差值分别显示。

K–R 不直接使用同伴套/敌方套信息。实现保留三个可选上下文修正，默认权重为 0，单独记录且不改变纯 K–R 数值：同伴套大牌数、敌方套大牌数、有明确将牌配合时的边花短门单位。不会默认叠加第二套牌型分。

## Profile 配置

```python
class Example(Profile):
    id = 'example'
    axioms = {
        # 原始 HCP 门槛；不是 K–R 研究中的总牌力门槛。
        'game_hcp': {'N': 25, 'H': 25, 'S': 25, 'C': 28, 'D': 28},
        'quality': {
            'threshold': 0.5,
            'partner_honors': 0,
            'opponent_honors': 0,
            'fit_shortage': 0,
        },
        'four_minor_exceptions': [
            {
                'source': 'example/gadget@1:call_spec:gf_start',
                'auction': '1CP2DP4CP',
                'calls': ['4C'],
            },
        ],
    }
```

省略配置时使用上述点力/质量默认值，4m 例外为空。例外必须同时声明来源、当前进程、允许的叫品；来源和进程均可显式使用 `*`。只有自然 4C/4D 适用，不能误把人工叫品当作可停定约。当前采用已同意花色的门槛，未同意花色时以 N 为评估目标；该简化可通过体系的公开配合状态与配置调整。

加载时拒绝未知配置、无效权重、矛盾接受/拒绝标志、非法标志和能够静态证明的错误 Pass 定义。策略函数无权关闭公理。

## 返回与界面

- `/api/bid`：`status` 为 `selected` 或 `blocked`，并带 `axioms`。
- `axioms`：`obligations`、`ranges`、`evidence`、`quality`、`rejected`、`errors`，另有当前 `auction`、`seat`。
- 错误包含代码、解释、叫品及规则来源；加载的规则来源包含 BSL 文件路径。
- `/api/simulate`：`status` 为 `complete`、`blocked` 或 `limit`。`blocked` 保存失败位置与公理报告；`calls`/`records` 仅含实际发生的叫牌。
- 体系定义错误返回 HTTP 422 及结构化 `errors`；运行时无候选返回正常响应中的 `blocked`。
- Table 保留失败前的回放，显示阻塞原因，不再不断重试相同局面；叫品提示展示公理摘要与 K–R/HCP。

无合规候选会报 `NO_COMPLIANT_CALL`，并保留各候选被排除的理由。当前不自动创造新的体系叫品。普通筛选与规则自相矛盾的错误分别记录；有合规候选可继续，但错误仍然展示。

## 满贯目的检测与通用 4NT 当前实现

`engine/slam_intent.py` 提供信息安全的满贯意图检测：只用行动方手牌和同伴的公开下限
（1NT 开叫后应叫方按 15 HCP 估算），不读取真实同伴牌。当前阈值：

- 无将：联手下限 ≥33、或“好的 32”（五张以上套、该套 9+ HCP、至少两张 A/K/Q 且 K–R 好）
  获得小满贯意图；≥37、或好的 36 获得大满贯意图。
- 有将：七张套且联手下限 ≥28，或六张套且 ≥30，获得小满贯意图；七张套 ≥33 或六张套
  ≥35 且将牌质量合格时获得大满贯意图。大满贯的有将阈值是工程默认值，等待体系确认。

自动记入关键张目的时，`Purpose` 现在保存 `grand_candidate` 和 `combined_min`。
在 4NT 问关键张得到公开答叫后：

- 缺至少两张关键张 → 五阶将牌止叫；
- 不缺关键张、将牌 Q 已确认且 `grand_candidate` 为真 → 直接叫七阶将牌；
- 其他不缺 A/Q 的情况 → 六阶将牌。

**尚未实现的部分**：自动启动 4NT 的完整策略、问 Q 的后续叫品、5NT 问 K 的答叫表，
以及“模拟判定小满贯合格/大满贯不合格后直接落位”的完整模拟流程。这些需要先确定
问 Q/问 K 的具体叫品和答叫约定，不能由实现者擅自补全。

独立公理、K–R 和引擎集成测试：在 `backend` 下运行：

```text
python -m unittest tests.test_axioms tests.test_axiom_integration tests.test_hand_quality tests.test_fallback -q
```

网页回归：启动前端后运行 `node frontend/tests/axioms.browser.cjs`；它模拟 API 的阻塞结果，验证有/无历史叫品、按钮禁用、错误文本安全渲染和重新发牌。

按用户要求，**Meow 2/1 体系的具体牌例迁移暂时搁置**。其旧断言仍保留，可能因为缺少公开范围、邀请接受/拒绝标志或续叫而失败；不通过降低公理约束或改写旧预期来掩盖。这些差异不等于公理独立测试失败。

公理层不读取发牌模拟中的真实同伴牌，也不以 DDS 分数自动改写硬约束。
另有独立的路线对照实验，可按公开证据采样并用 DDS 评估最终定约；
该报告尚不选择叫品。本版不实现自动候选补全、满贯邀请专用公理、
局况相关门槛或复杂的竞争惩罚选择。范围宽度为 0 的邀请处理仍显式报错，等待体系约定。

## 同伴实力范围的模拟推断（后续重要手段）

当一个公开叫品没有在 public meaning 里写出精确的 HCP/K–R 范围（典型如扣叫），
不要用固定经验值代替；应通过**模拟「同伴持什么牌会这样叫」**反推它的范围。

做法：

1. 用已有的公开证据约束同伴：已叫花色长度、HCP 下界、已示控制、将牌，
   以及此前叫品已承诺的范围。
2. 在约束内采样若干手牌，逐手回放本进程，只保留**会作出该叫品**的牌。
3. 用保留样本统计同伴的 HCP/K–R 分布，取所需分位（例如 10% 分位）作为
   该进程的实力代表，而不是用全体样本。
4. 扣叫自身的公开强度从上一位叫品推导：被严肃性 3NT 逼迫的扣叫沿用上一口
   范围、无新信息；自愿扣叫的 K–R 下限 +2；若原范围宽度不足 2 点，则改为
   二分原范围、取高的一半（详见 `docs/15_daqiush_slam.md`）。

这条「用模拟反推同伴范围」是后续扣叫、满贯与竞争叫牌的核心手段：凡缺少
机器可读范围的公开叫品，都应优先用它，而不是硬编码范围。它仍然只使用公开
证据与采样出的假设手牌，不读取真实同伴牌。

## 扣叫续叫的满贯政策（实现中）

在同伴扣叫、且其范围仍未知时，本方可按三路判定：即使同伴无额外实力也能
合格（关键张不缺 2A/1A1Q）→ 4NT；即使同伴 +2KR 额外实力仍不合格 → 成局
止叫（同伴可用同一套模拟否决）；否则继续扣叫。满贯是否合格优先用便宜的
确定性判据，无法判定时才回退 DDS。高花允许扣过 4M（需模拟收益为正），
低花禁止扣过 5m 找小满贯。判定核心见 `backend/engine/cue_slam_policy.py`；
selector 接线与扣叫 public evidence 补全尚未完成。
